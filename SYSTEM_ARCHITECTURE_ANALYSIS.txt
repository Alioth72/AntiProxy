STORAGE DETAILS
---------------

Face embeddings are stored in PostgreSQL:
    Table: face_embeddings
    Fields:
        - id (BIGINT, primary key)
        - person_name (TEXT, unique) - Student's full name
        - person_id (TEXT, nullable) - Email or roll_no
        - embedding (REAL[]) - 512-dimensional vector
        - created_at, updated_at (TIMESTAMP)

Matching Strategy:
    - Person uniqueness determined by person_name field
    - person_id is stored but NOT USED for matching
    - When student uploads new photo, existing person_name is updated

ISSUE: Name-based storage means:
    - Multiple students with same name cause conflicts
    - Names with typos won't match DB names
    - No direct link between face and roll_no

5. FACE RECOGNITION & ATTENDANCE MARKING
================================================================================

CURRENT IMPLEMENTATION (NAME-BASED MATCHING)
-------------------------------------------

Teacher App Flow:
Location: /frontend_teacher/lib/ui/classes/face_recognition_attendance_page.dart
         (lines 180-300)

Step 1: Send Image to Face-API
    Endpoint: POST /recognize_faces
    Payload: {"image_data": "base64_encoded_image"}
    
Step 2: Face-API Processing
    Location: /face-api-source-v2/app.py (lines 316-450)
    Process:
        a. Decode base64 image
        b. Detect all faces in image
        c. For each detected face:
           - Align face using landmarks
           - Extract 512-dim embedding
           - Find best match in face_embeddings table using cosine similarity
           - Calculate similarity score (0.0 to 1.0)
        d. Return JSON response:
           {
               "results": [
                   {
                       "boundingBox": {"left": x, "top": y, "width": w, "height": h},
                       "name": "Student Name",
                       "similarityScore": 0.85
                   },
                   ...
               ],
               "annotatedImageBase64": "..."
           }

Step 3: Teacher App Matching Logic (NAME-BASED)
    Location: /frontend_teacher/lib/ui/classes/face_recognition_attendance_page.dart
             (lines 191-290)
    
    For each recognition result:
        1. Check if similarity_score >= threshold (default 0.72)
        2. If above threshold, try matching strategies in order:
           
           Strategy 1: EXACT MATCH
               Compare result.name (lowercase) == student.name (lowercase)
               Example: "shubhank gupta" matches "Shubhank Gupta"
           
           Strategy 2: NORMALIZED MATCH
               Remove special chars, normalize spaces
               Example: "Shubhank  Gupta!" matches "Shubhank Gupta"
           
           Strategy 3: FIRST NAME MATCH
               If recognized name is single word, match first name only
               Example: "Shubhank" matches "Shubhank Gupta"
           
           Strategy 4: PARTIAL MATCH (CONTAINS)
               Either name contains the other (min 3 chars)
               Example: "Shubhank" matches "Gupta Shubhank"
        
        3. First match wins - mark student as PRESENT
        4. Store in _studentStatuses[student.rno] = 'present'
        5. Track matchedRollNumbers to prevent duplicates

Step 4: Submit Attendance to Backend
    - Teacher reviews marked attendance
    - Clicks "Submit Attendance"
    - App sends to: PUT /attendance/sessions/{session_id}/statuses
    - Payload includes: studentId (UUID), status, recognizedByAi (bool), 
                       similarityScore (float)

PROBLEM WITH CURRENT APPROACH
-----------------------------

Face-API Response:
    {
        "name": "Shubhank Gupta",    <- ONLY NAME, NO ROLL_NO
        "similarityScore": 0.85
    }

Teacher App Matching:
    - Loops through class roster (list of Student objects)
    - Each Student has: {id, name, rno, email, ...}
    - Compares result.name with student.name
    - If match, marks student.rno as present

Issues:
    1. Name variations cause mismatches:
       - DB: "Shubhank Gupta"
       - Face-API: "Shubhank" (incomplete enrollment)
       - Face-API: "SHUBHANK GUPTA" (case mismatch)
    
    2. Multiple students with similar names:
       - "Aman Kumar" and "Aman Singh" -> confusion
       - "Priya" alone matches both "Priya Sharma" and "Priya Gupta"
    
    3. No direct identifier:
       - Face-API stores person_id (roll_no) but doesn't return it
       - Matching relies on fuzzy name comparison
       - No guarantee of correct student

Proposed New Method:
    def find_best_match_with_id(self, embedding, similarity_threshold=0.0):
        """
        Find best match and return complete person data.
        
        Returns:
            dict: {
                "name": person_name,
                "person_id": person_id,
                "similarity": similarity_score
            } or None
        """
        best_match = None
        best_similarity = -1.0
        best_person_id = None
        
        emb_array = np.array(embedding)
        
        with self._lock:
            for person_name, person_data in self._cache.items():
                ref_embedding = np.array(person_data['embedding'])
                similarity = self._cosine_similarity(emb_array, ref_embedding)
                
                if similarity > best_similarity:
                    best_similarity = similarity
                    best_match = person_name
                    best_person_id = person_data.get('person_id')
        
        if best_similarity > similarity_threshold:
            return {
                "name": best_match,
                "person_id": best_person_id,
                "similarity": best_similarity
            }
        else:
            return None

BENEFITS OF ROLL_NO MATCHING
----------------------------

1. EXACT IDENTIFICATION
   - Roll numbers are unique (students.roll_no has UNIQUE constraint)
   - No ambiguity with similar names
   - Direct mapping: face -> roll_no -> student record

2. ELIMINATES NAME MATCHING ERRORS
   - No more fuzzy string matching
   - No case sensitivity issues
   - No partial name confusion

3. HANDLES NAME CHANGES
   - If student changes name in DB, face remains linked to roll_no
   - No need to re-upload photos after name corrections

4. FASTER MATCHING
   - O(1) lookup by roll_no instead of O(n) name comparison
   - No need for multiple fallback strategies

5. BETTER AUDIT TRAIL
   - Clear link: face embedding -> roll_no -> student UUID
   - Can verify: "Which roll_no was recognized at timestamp X?"
